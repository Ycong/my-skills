# Dev Review Workflow（开发审核流程编排）

本 skill 是流程编排层（规定"怎么转"）。审核标准（"审什么"）来自**当前项目根目录**的 `review-checklist.md`——由各项目自行维护，含项目红线。`review-checklist-base.md` 仅为母版，绝不作为审核标准加载。

## 启动前置检查

1. 在当前项目根目录找 `review-checklist.md`。
2. 找不到 → 停止，告知用户需先复制 `review-checklist-base.md` 到项目根目录、重命名为 `review-checklist.md`、填好第四节红线。可主动代为完成复制与改名，但红线内容必须由用户确认。
3. 找到 → 检测项目根目录的 `.review-workflow-state`（跨会话状态文件）：
   - 存在未完成流程 → 向用户报告其中进度（需求、分级、当前步骤、材料路径），询问续跑还是作废；续跑则从记录的步骤继续，作废则删除该文件后从头发起
   - 不存在 → 正常发起

## 流程总览

```
发起 → 判定 L0（微小改动）→ 是 → 直通：① 直通卡确认 → ② 主会话直接改 → ③ 贴验收原始输出 → ④ 过目 diff → 结束
                          → 否 → ① 方案 → ② 分级（人工确认）→ ③ 审核（subagent）→ ④ 放行/驳回
                               → ⑤ 执行 → ⑥ 验收（subagent）→ ⑦ 结论（仅异常上报人工）
```

## 跨会话状态持久化

- 每完成一步，立即更新项目根目录的 `.review-workflow-state`：需求摘要、风险分级、当前步骤、方案与审核结论要点、关键材料路径（方案文档、diff、验收清单）
- **冻结**：第 2 步确认的风险分级与 `review-checklist.md` 版本冻结到第 7 步——中途不改分级、不改 checklist（改前部内容会让后续每轮上下文全价重算，也让已过的门禁失效）；确需变更 → 显式记录变更点，并重跑受影响的门禁（第 3/6 步）
- 第 7 步得出最终结论后删除该文件
- 首次创建该文件时提醒用户将其加入 `.gitignore`（流程状态不进版本库）

## 步骤规则

**0. L0 直通（微小改动，全程 1 次交互）**
只用于"改动比流程开销还小"的情形。**下列条件必须全部满足**：改动不超过 2 个文件，且这 2 个文件**同属一个模块/目录**（跨模块改动不进 L0）；不命中 L1 判定原则；不命中项目红线；改动量约 ≤100 行且不新增公共接口/依赖；有可自动执行的验收命令（纯文档/注释类可无）。任一不满足或存疑 → 不进 L0，按常规分级走（存疑从高）。
**行数只是线索，不是判据**：改动哪怕只有几行，只要命中并发语义、状态机转换、幂等/重试语义、配置生效面等推理密集型内容，同样不进 L0。

流程（只有 1 个人工介入点）：
1. 主会话给"直通卡"三行：**改什么 / 动哪些文件 / 验收命令**，请用户确认（复用介入点 1，秒批）
2. 确认后**主会话直接改**——不写方案文档、不派审核、不派实现子代理
3. 跑验收命令，把**原始输出**贴出来（不得自评"通过"）
4. 贴出 `git diff` 供过目，结束

硬性升级规则（任一命中**立即停止**，已改内容作为方案输入，回到第 2 步重新分级）：
- 改动溢出到第 3 个文件、超出约 100 行、第 2 个文件不在同一模块/目录，或命中项目红线
- 验收命令缺失或不为绿
- 同一文件/模块已连续走过 2 次 L0（第 3 次起走常规流程，防化整为零）

L0 不写方案文档、不写 `.review-workflow-state`；直通卡与验收原始输出留在会话记录里。
一旦进入第 1 步（常规流程），不得中途退回 L0。
注：L0 的**准入条件**定义在项目 `review-checklist.md` 的分级表里（母版 `review-checklist-base.md` 已含该行）；本文件只管它**怎么走**。两处不一致时以 checklist 为准，且取更严的一侧。

**1. 方案产出（AI）**
必须包含四要素：影响面、风险分级建议及理由、回滚方案、可执行验收清单（能自动化的验收项必须落为测试或脚本）。缺任一项直接退回重写，不进入审核。
可选增强（若环境中已安装对应 skill）：需求模糊或边界不清时，先调用 `grill-with-docs` 澄清再成文；澄清完成后可调用 `to-spec` 将结论标准化成文；需求过大需拆分时，调用 `to-tickets` 拆成带阻塞关系的工单，逐工单走本流程（工单可整体沿用一次分级，或按第 2 步各自分级）。未安装则直接产出方案，不阻塞。

**2. 分级判定（AI 预判 + 人工确认）**
- AI 按判定原则预判并写明理由：不看功能"像什么"，看它失效或误用时波及什么
- 命中 L1 判定原则（核心链路、资金/资产、数据破坏、安全边界）→ 强制 L1，不得降级；存疑从高
- 人工确认分级后才继续（L2/L3 可秒批，确认动作不可省）

**3. 审核（subagent）**
- L3 免审，直接执行
- L2 起单个审核 subagent
- L1 起并行审核（建议：安全边界/失效路径一个，并发资源一个）
- 材料三样：方案文档、项目的 review-checklist.md、相关代码路径（**只给入口路径/符号名，按需自行扩大范围**，不要预读整仓或整文件）
- prompt 用文末模板，不得即兴发挥

**4. 放行 / 驳回**
- 无 blocking：L2 自动放行；L1 等人工确认 blocking 清空
- 有 blocking：驳回 → 修正 → 仅重审 diff 修正部分 → 回到本步
- 修正必须带**新证据**（具体哪一条不成立、改了什么、如何已验证）；只回"已修好，再看一遍"不进重审

**5. 执行（AI）**
只做已批准范围。diff 即验收材料，不得夹带。开发方式按分级约束：

- L1：强制 TDD——从验收清单先写失败测试，再实现，循环至全绿；重构不得改变已批准行为。若环境中已安装 `tdd` skill 则调用它执行循环，未安装按本条内联规则执行
- L2：测试与实现同 diff 交付，交付时全绿（不强制先后）；多工单且工单间无阻塞时，可并行实现，但每工单独立产出 diff 并独立走第 6 步验收
- L3：免测试
- 并行边界：L1 永远单工单串行 TDD，禁用并行实现；并行仅限 L2 无阻塞工单，任何并行不得合并各工单的 diff 与验收
- 通用：diff 必须包含验收清单中可自动化项对应的测试/脚本；确实无法自动化的，须在验收清单中显式改标为人工项并写明理由（该理由进入验收材料，可见即受审）
- 执行止损：连续 **3 轮**验收命令不为绿，或同一失败反复出现 → 停止，不得继续重试或换法硬试；上报原始失败输出 + 已试过的方向（L1/L2 同样适用）
- 派发准入（第 3/5/6 步共同适用）：子任务要能**精简交代**（不靠复述大段试错史）且产出可独立验收，才拆给 subagent；需要大篇幅解释推导假设的属高耦合连续推理，宁可整体作为一个工单走一次，也不要硬拆成多个 subagent（每次派发都要付冷启动与交接成本）

**6. 验收（subagent）**
材料：diff、验收清单、项目的 review-checklist.md。可自动化项必须实际运行测试/脚本，全绿报告作为放行凭证。
- 回传契约：详细证据落盘（如 `docs/verify-*.md`），回传只给**结论 + 未通过项 + 路径**；终端输出只贴失败段（通过项折叠为一行摘要，退出码原样保留），不得把整段日志倒回主会话

**7. 结论**
- 通过 → 结束
- 有条件通过 → 遗留 non-blocking 项上报人工过目后结束
- 驳回 → 修正（同样要带新证据）→ 仅重审 diff → 回到第 6 步；连续两轮未过 → 人工裁决

## 人工介入点（全流程仅此四个，不得增加也不得跳过）

| # | 时机 | 动作 |
|---|---|---|
| 1 | 第 2 步 | 确认风险分级 |
| 2 | 第 4 步 | 确认 L1 blocking 清空，批准执行 |
| 3 | 第 7 步 | 过目有条件通过的遗留项 |
| 4 | 验收驳回且修正两轮未过 | 人工裁决 |

L0 直通只用介入点 1（直通卡确认）；L0 结束时贴 diff 供过目是**告知动作**，不是新增门禁。

## subagent prompt 模板

**方案审核**

```text
你是独立审核人，与方案作者无共享上下文，不得迁就方案的自评结论。
材料：方案文档 {路径}、审核标准 {项目review-checklist.md路径}、相关代码 {入口路径/符号名列表，按需自行扩大范围}。
逐条核对 checklist 各节；以代码与配置实况为准，不信任方案描述。
输出：结论（通过/有条件通过/驳回）+ blocking 列表 + non-blocking 列表，
每条附代码位置或方案章节。
输出形态：结论先行（答案在前，解释在后）；删寒暄、铺垫、对冲词与结尾复述；
术语、代码、路径、JSON 与报错一字不删；安全或不可逆操作相关判断用完整句子说清。
工具优先级：查定义/调用链/波及面优先用 codegraph（MCP 工具 `codegraph_explore`，或经 bash 调
`codegraph explore|impact|callers|callees|node --json`）；不可用再退回 grep 定位 + read 验证；
调用关系一目了然的小项目不必强用。结论里注明用了哪条路；缺工具就说明缺什么，不要靠猜。
```

**执行验收**

```text
你是独立验收人，与执行者无共享上下文。
材料：diff {路径或范围}、验收清单 {路径}、审核标准 {项目review-checklist.md路径}、相关代码 {入口路径/符号名列表，按需自行扩大范围}。
逐条执行验收：可自动化项必须实际运行测试/脚本并附输出；人工项给出核对证据。
同时核对：diff 无夹带、blocking 项代码层复核、偏差全部披露。
输出：结论 + 各验收项结果 + 偏差与遗留清单。
输出形态：结论先行（答案在前，解释在后）；删寒暄、铺垫、对冲词与结尾复述；
术语、代码、路径、JSON 与报错一字不删；安全或不可逆操作相关判断用完整句子说清。
工具优先级：查调用链/波及面/受影响测试优先用 codegraph（MCP 工具 `codegraph_explore`，或经 bash 调
`codegraph impact|callers|affected|node --json`）；不可用再退回 grep + read；小项目不必强用。
证据里注明用了哪条路；缺工具就说明缺什么，不要靠猜。
```
