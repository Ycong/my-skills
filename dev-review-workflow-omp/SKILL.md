# Dev Review Workflow（开发审核流程编排 · omp 适配版）

> 本文件是 `../dev-review-workflow/SKILL.md` 的 **oh-my-pi（omp）专用适配版**，原版不动、两版并行维护。
> 通用变更同步流程：先改原版，再把差异移植到本文件。本版的主线差异只有一条——
> 把泛指的 "subagent" 落成 omp 命名子代理，并把第 5 步从"主会话执行"改为"按分级派发"。
> 完整差异清单见本目录 README.md 的"与通用版的差异边界"（共五类，可 diff 验证）。
>
> 本 skill 是流程编排层（规定"怎么转"）。审核标准（"审什么"）来自**当前项目根目录**的
> `review-checklist.md`——由各项目自行维护，含项目红线。`review-checklist-base.md` 仅为母版，绝不作为审核标准加载。

## 运行环境与角色分派（omp 专属）

本 skill 依赖四个**命名子代理**（omp：放在 `~/.omp/agent/agents/` 下的 markdown 定义，frontmatter 指定模型与 `output` JSON Schema）：

| 编排角色 | omp agent 定义 | 模型 | 出现步骤 |
|---|---|---|---|
| 方案审核 | `reviewer` | 强模型（`@slow`） | 第 3 步 |
| 核心实现 | `core-dev` | 强模型（frontmatter 显式指定） | 第 5 步（L1） |
| 常规实现 | `implementer` | 快模型（`@task`） | 第 5 步（L2/L3） |
| 独立验收 | `verifier` | 强模型（`@slow`） | 第 6 步 |

**不变式（全流程最高优先级，**L0 直通是唯一例外**）：主会话除 L0 外全程不产出 diff。** 所有写文件、跑会改动的动作都发生在子代理里；主会话只做只读动作（读 checklist、收集 `git diff`、更新状态文件）。环境缺任一子代理定义 → 停止并提示安装，**不降级为主会话亲自执行**——降级等于放弃"持有全局记忆的上下文里没有 diff"这条纪律。
L0 之所以例外：微小改动的派发开销（规格卡 + 一个无上下文的新会话 + diff 收集）大于改动本身，硬塞进派发链只会让流程失真；L0 用硬性升级条件（见第 0 步）代替审核与验收子代理。

风险分级与实现的映射（第 5 步用）：

| 风险级别 | 实现者 | 理由 |
|---|---|---|
| L1 | `core-dev`（强模型） | 核心链路/资金/数据/安全，值得强模型 + 强契约约束 |
| L2 | `implementer`（快模型） | 规格完备时快模型表现相当，成本约 1/3 |
| L3 | `implementer`（快模型），免审 | 纯文档/展示，不值得强模型 |

## 启动前置检查

1. 在当前项目根目录找 `review-checklist.md`。
2. 找不到 → 停止，告知用户需先复制 `review-checklist-base.md` 到项目根目录、重命名为 `review-checklist.md`、填好第四节红线。可主动代为完成复制与改名，但红线内容必须由用户确认。
3. 找到 → 检测项目根目录的 `.review-workflow-state`（跨会话状态文件）：
   - 存在未完成流程 → 向用户报告其中进度（需求、分级、当前步骤、材料路径），询问续跑还是作废；续跑则从记录的步骤继续，作废则删除该文件后从头发起
   - 不存在 → 正常发起
4. 检测四个子代理定义是否**确实是本 skill 的那四个**（只按 name 找到不算数——omp 内置 agent 里也有 `reviewer`，用户级文件缺失时会静默命中内置版本，而内置版本没有本 skill 要求的 `output` 契约）：
   - `~/.omp/agent/agents/` 下必须存在 `reviewer.md` / `core-dev.md` / `implementer.md` / `verifier.md` 四个文件
   - 从项目根向上逐级检查 `.omp/agents/`，不得存在同名文件（项目级定义优先于用户级，会静默顶掉本 skill 的定义）
   - 任一条不满足 → 停止并列出缺哪个文件、被哪个路径顶掉，等用户补齐

## 流程总览

```
发起 → 判定 L0（微小改动）→ 是 → 直通：① 直通卡确认 → ② 主会话直接改 → ③ 贴验收原始输出 → ④ 过目 diff → 结束
                          → 否 → ① 方案 → ② 分级（人工确认）→ ③ 审核（reviewer）→ ④ 放行/驳回
                               → ⑤ 执行（L1→core-dev，L2/L3→implementer）→ ⑥ 验收（verifier）→ ⑦ 结论（仅异常上报人工）
```

## 跨会话状态持久化

- 每完成一步，立即更新项目根目录的 `.review-workflow-state`：需求摘要、风险分级、当前步骤、方案与审核结论要点、关键材料路径（方案文档、diff、验收清单）
- 第 7 步得出最终结论后删除该文件
- 首次创建该文件时提醒用户将其加入 `.gitignore`（流程状态不进版本库）

## 步骤规则

**0. L0 直通（微小改动，全程 1 次交互，由主会话执行、不派发子代理）**
只用于"改动比流程开销还小"的情形。**下列条件必须全部满足**：改动不超过 2 个文件；不命中 L1 判定原则；不命中项目红线；改动量约 ≤100 行且不新增公共接口/依赖；有可自动执行的验收命令（纯文档/注释类可无）。任一不满足或存疑 → 不进 L0，按常规分级走（存疑从高）。

流程（只有 1 个人工介入点）：
1. 主会话给"直通卡"三行：**改什么 / 动哪些文件 / 验收命令**，请用户确认（复用介入点 1，秒批）
2. 确认后**主会话直接改**——不写方案文档、不派 `reviewer`、不派 `core-dev` / `implementer`
3. 跑验收命令，把**原始输出**贴出来（不得自评"通过"）
4. 贴出 `git diff` 供过目，结束

硬性升级规则（任一命中**立即停止**，已改内容作为方案输入，回到第 2 步重新分级）：
- 改动溢出到第 3 个文件、超出约 100 行、或命中项目红线
- 验收命令缺失或不为绿
- 同一文件/模块已连续走过 2 次 L0（第 3 次起走常规流程，防化整为零）

L0 不写方案文档、不写 `.review-workflow-state`；直通卡与验收原始输出留在会话记录里。
一旦进入第 1 步（常规流程），不得中途退回 L0。
注：L0 的**准入条件**定义在项目 `review-checklist.md` 的分级表里（母版 `review-checklist-base.md` 已含该行）；本文件只管它**怎么走**。两处不一致时以 checklist 为准，且取更严的一侧。

**1. 方案产出（主会话，元工作）**
必须包含四要素：影响面、风险分级建议及理由、回滚方案、可执行验收清单（能自动化的验收项必须落为测试或脚本）。缺任一项直接退回重写，不进入审核。
可选增强（若环境中已安装对应 skill）：需求模糊或边界不清时，先调用 `grill-with-docs` 澄清再成文；澄清完成后可调用 `to-spec` 将结论标准化成文；需求过大需拆分时，调用 `to-tickets` 拆成带阻塞关系的工单，逐工单走本流程（工单可整体沿用一次分级，或按第 2 步各自分级）。未安装则直接产出方案，不阻塞。
方案文档写入 `docs/`，主会话只写文档不写代码。

**2. 分级判定（主会话预判 + 人工确认）**
- 按判定原则预判并写明理由：不看功能"像什么"，看它失效或误用时波及什么
- 命中 L1 判定原则（核心链路、资金/资产、数据破坏、安全边界）→ 强制 L1，不得降级；存疑从高
- 人工确认分级后才继续（L2/L3 可秒批，确认动作不可省）

**3. 审核（`reviewer` 子代理，强模型）**
- L3 免审，直接执行
- L2 起单个 `reviewer`
- L1 起并行审核（建议：安全边界/失效路径一个，并发资源一个，两个 `reviewer` 并行互不通气）
- 材料三样：方案文档、项目的 review-checklist.md、相关代码路径
- prompt 用文末模板，不得即兴发挥
- 结构化返回由 `reviewer` 定义的 `output` JSON Schema 保证；缺 blocking/non-blocking 字段的返回视为无效，重派

**4. 放行 / 驳回（主会话）**
- 无 blocking：L2 自动放行；L1 等人工确认 blocking 清空
- 有 blocking：驳回 → 修正 → 仅重审 diff 修正部分 → 回到本步

**5. 执行（分派给实现子代理，主会话不写代码）**
主会话把已批准方案转成**规格卡**（目标一句话 / 输入要改哪些文件 / 输出期望行为 / 边界不许碰的目录 / 验收命令）后按分级派发。只做已批准范围，diff 即验收材料，不得夹带。

- **L1 → `core-dev`**：单工单串行，禁用并行。规格卡附 TDD 指令——从验收清单先写失败测试，再实现，循环至全绿；重构不得改变已批准行为。若环境中已安装 `tdd` skill，在规格卡里注明让 core-dev 参照执行，未安装按内联规则执行
- **L2 → `implementer`**：测试与实现同 diff 交付，交付时全绿（不强制先后）；多工单且工单间无阻塞时，可并行实现（omp `task.maxConcurrency` 设上限），但每工单独立产出 diff 并独立走第 6 步验收
- **L3 → `implementer`**：免测试、免审
- **并行边界**：L1 永远单工单串行 TDD；并行仅限 L2 无阻塞工单，任何并行不得合并各工单的 diff 与验收
- **diff 收集（主会话唯一涉及的"代码"动作，且是只读）**：子代理返回后，主会话跑 `git diff` 收集实际改动作为验收材料。子代理申报的 `files_changed` 与 `git diff` 不符 → 按夹带处理，直接进第 6 步判驳回
- **通用**：diff 必须包含验收清单中可自动化项对应的测试/脚本；确实无法自动化的，须在验收清单中显式改标为人工项并写明理由（该理由进入验收材料，可见即受审）

**6. 验收（`verifier` 子代理，独立执行体）**
材料：diff（主会话收集的 git diff）、验收清单、项目的 review-checklist.md。可自动化项必须实际运行测试/脚本，全绿报告作为放行凭证。
- verifier 与第 5 步的实现子代理**必须是不同的执行体**，不复用其任何输出，干净重跑
- 实现者若偏离规格（core-dev 的 `contract_deviations`、implementer 的 `notes`），偏差原文随材料一并给 verifier 复核
- 结构化返回由 `verifier` 定义的 `output` JSON Schema 保证：偏差与遗留必须落在 `deviations` / `leftovers`（无则空数组），**不得塞进 `checks` 伪装成一条验收项**；`overall` 只由 `checks` 决定；缺这两个字段的返回视为无效，重派

**7. 结论（主会话）**
- 通过 → 结束
- `verifier` 的 `leftovers` 非空 → 按"有条件通过"处理（遗留项上报人工过目后结束）；`deviations` 非空 → 先按偏差逐条复核再定结论
- 有条件通过 → 遗留 non-blocking 项上报人工过目后结束
- 驳回 → 修正 → 仅重审 diff → 回到第 6 步；连续两轮未过 → 人工裁决

## 人工介入点（全流程仅此四个，不得增加也不得跳过）

| # | 时机 | 动作 |
|---|---|---|
| 1 | 第 2 步 | 确认风险分级 |
| 2 | 第 4 步 | 确认 L1 blocking 清空，批准执行 |
| 3 | 第 7 步 | 过目有条件通过的遗留项 |
| 4 | 验收驳回且修正两轮未过 | 人工裁决 |

L0 直通只用介入点 1（直通卡确认）；L0 结束时贴 diff 供过目是**告知动作**，不是新增门禁。

## subagent prompt 模板

派发时以 omp 命名子代理发起（agents 目录按 `name` 匹配），模板文本作为 prompt 传入；返回结构由各 agent 定义的 `output` JSON Schema 兜底。
各 agent 的 `output` 中 `slice` 是必填字段（模板文本不含它），派发时明确告知填规格卡编号或一句话标识——不说明会被子代理猜。

**方案审核（→ `reviewer`）**

```text
你是独立审核人，与方案作者无共享上下文，不得迁就方案的自评结论。
材料：方案文档 {路径}、审核标准 {项目review-checklist.md路径}、相关代码 {路径列表}。
逐条核对 checklist 各节；以代码与配置实况为准，不信任方案描述。
输出：结论（通过/有条件通过/驳回）+ blocking 列表 + non-blocking 列表，
每条附代码位置或方案章节。
```

**执行验收（→ `verifier`）**

```text
你是独立验收人，与执行者无共享上下文。
材料：diff {路径或范围}、验收清单 {路径}、审核标准 {项目review-checklist.md路径}。
逐条执行验收：可自动化项必须实际运行测试/脚本并附输出；人工项给出核对证据。
同时核对：diff 无夹带、blocking 项代码层复核、偏差全部披露。
输出：结论 + 各验收项结果 + 偏差与遗留清单。
```

**实现派发（→ `core-dev` / `implementer`，附在规格卡后）**

```text
只对本规格卡负责。先跑验收命令建立基线，再按输入/输出/边界实现，最后重跑验收命令。
不碰边界以外的文件；规格有歧义或与实现冲突，停下来申报，不要静默偏离、不要扩大范围。
返回：files_changed 与验收命令的原始输出；偏离规格之处必须显式申报。
```
